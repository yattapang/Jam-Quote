# Design — client-generated ids, row versions, and tombstones

**Status: Proposed.** Awaiting the owner's approval (Rule 1.1). No migration is written until then.

**Brief:** §18 step 1, Foundations — "schema (including client-generated IDs and versioning for
future sync)". One of the three items that keep step 1 incomplete.
**Rules:** 1.1, 2, 6 (versioned migrations, soft deletes where history matters), 8, 12 (offline).
**Decisions it touches:** ADR 0012 (conventions), and it will need an ADR of its own.

---

## 1. The problem, and why now

Offline mobile use is §18 step 4 work, but the brief deliberately puts *its schema requirements* in
step 1. The reason is worth restating because it is the whole argument for doing this before
anything else: **a sync model cannot be retrofitted onto rows that were not built for it.**

Three specific things sync needs that the schema does not have:

1. **The client must choose the id.** A contractor prices a job on a phone with no signal. The quote
   exists, has lines, and is referenced by other rows — all before the server has ever seen it. If
   the server assigns the id on arrival, the phone has to rewrite every local reference afterwards,
   and a retry that the server already processed creates a *second* quote. Client-generated ids make
   the upload **idempotent**: the same id arriving twice is the same row.
2. **A row must say which version it is.** Two people edit the same quote, or a phone uploads an
   edit made against a stale copy. Without a version, last-write-wins silently, and the loser never
   learns. With one, a stale write is *refused* and the conflict becomes visible.
3. **A deletion must be discoverable.** A row deleted on the server is, to a phone that has been
   offline, indistinguishable from a row it has not been told about yet — so it comes back. Sync
   needs a tombstone.

Today there are 8 tables. Every table added before this lands is a table to retrofit, and the
retrofit is a migration plus a backfill plus every query that touched it.

## 2. What this must achieve

1. A client can create a row **and its children** offline, upload them in any order, and upload
   twice, with the second upload changing nothing.
2. A write made against a stale copy of a row is **refused**, not silently applied.
3. A deleted row is distinguishable from an unknown row, for a client that has been away.
4. Every tenant-owned table follows the convention — enforced by a guard, not by memory.
5. The cost to a reader is one paragraph of explanation, not a framework.

## 3. The shape

### 3.1 Ids: UUIDv7, generated by whoever creates the row

```
id  UUID PRIMARY KEY     -- chosen by the client when the client creates the row
```

**UUIDv7, not v4.** v7 embeds a millisecond timestamp in its leading bits, so ids sort roughly by
creation time. That buys two things that matter at our scale and cost nothing: inserts land at the
**end** of the primary-key index instead of scattering across it, and "most recent first" needs no
extra column. v4's randomness fragments the index on every insert.

**What v7 gives away, stated rather than glossed:** the creation time of the row, to anyone holding
the id. For our rows that is not sensitive — a quote's own customer can see its date on the
document. **It would matter for a share token**, which is why a share token is a separate random
secret and never a row id. Recorded here so nobody later "simplifies" by putting a v7 id in a
public URL and treating it as unguessable: **a v7 id is not a secret.**

**One generator, in core** — `newRowId()` — used by api, web and mobile. Postgres keeps a
`gen_random_uuid()` default as a **safety net for rows created by SQL** (a migration, a seed, an
admin script), not as the normal path. The default being v4 while the app writes v7 is a deliberate
mismatch: a v4 id in the data is a signal that a row was made outside the application.

### 3.2 Versions: an integer, compared on write

```
version  INTEGER NOT NULL DEFAULT 1
```

Every update is a **compare-and-set**:

```sql
UPDATE quote SET ..., version = version + 1, updated_at = now()
 WHERE id = $1 AND version = $2
```

Zero rows affected means somebody else got there first, and the caller is told so rather than
having their write vanish. This is optimistic concurrency, and it is the same mechanism sync needs
for conflict detection — one column, two jobs.

**Why not `updated_at` for this.** Clocks disagree, two writes inside the same millisecond are
indistinguishable, and a clock that moves backwards makes a stale write look fresh. `updated_at`
stays, for humans and for cursors; it is not the concurrency check.

**Why not Postgres's `xmin`.** Free and automatic, but it is a system column that wraps, is not
portable, and cannot be read by a client to send back. Rule 10 wants portable.

### 3.3 Tombstones

```
deleted_at  TIMESTAMPTZ(6)      -- NULL means live
```

Soft delete where history matters (Rule 6), and it is what lets a client learn a row is gone. The
cost is real and must be paid deliberately: **every query filters `deleted_at IS NULL`**, and the
audit found the previous application had soft deletes everywhere and **indexes that ignored them**,
so every list query filtered rows the index had already returned. So: indexes on tenant-owned
tables are **partial**, `WHERE deleted_at IS NULL`.

**Not every table gets one.** A tombstone on `app_session` or `rate_limit_bucket` is meaningless —
nothing syncs them and nothing references them historically. The convention applies to
**tenant-owned business data**, and the guard's exemption list names the rest with reasons, exactly
as the RLS coverage guard does.

### 3.4 What a sync cursor will be, and what is deliberately not decided

A client asks "what changed since X?". The honest answer today is `updated_at > X`, ordered by
`(updated_at, id)` — the id breaking ties so a page boundary cannot skip or repeat a row.

**Its limit, named now rather than discovered later:** `updated_at` comes from a clock. Two rows
written in the same millisecond, or a clock correction, can produce a cursor that skips a row.
A per-tenant monotonic sequence would fix it and costs a shared counter on every write. **That
decision belongs to the sync design**, not here; this design's job is to make sure the columns
exist so that either answer is available. Recorded as owed.

## 4. Trade-offs

- **A client-chosen id is a client-supplied value**, and those are never trusted. It is validated
  as a UUID and it does **not** confer ownership: the row's `tenant_id` still comes from the
  session (core/tenancy), so a phone cannot create a row in another tenant by choosing a clever id.
  Worth stating because "the client picks the primary key" sounds alarming until you see that the
  tenant boundary is elsewhere.
- **Compare-and-set makes every update wordier.** Accepted: it is the difference between a lost
  edit and a reported conflict.
- **Soft deletes complicate every query.** Accepted, with partial indexes, because sync and history
  both need them. The alternative — hard deletes plus a separate tombstone table — is more moving
  parts for the same outcome.
- **v7 ids leak creation time.** Accepted for rows; refused for anything public.

## 5. How it will be proved

| Plant | Must fail |
|---|---|
| A tenant-owned table added with no `version` | the convention guard |
| A tenant-owned table added with no `deleted_at` | the convention guard |
| A non-partial index on a table that has `deleted_at` | the index guard |
| `newRowId()` returning a v4 (or a non-monotonic sequence) | the id generator's test |
| A second insert of the same id | the idempotency test (one row, not two, and no error surfaced to the caller) |
| A compare-and-set update with a stale version | the concurrency test (zero rows affected, the row unchanged) |
| An update that forgets `version = version + 1` | the version-increment test |

Plus: two concurrent updates against the same version, where exactly one wins — run against a real
database, because the claim is about what the database does.

**Not proved by any of this:** that sync works. There is no sync. This makes the schema capable of
it, and the sync design will have to demonstrate the rest.

## 6. Scope

**In:** the three columns and the id generator; a migration adding them to the existing tenant-owned
tables (`tenant`, `app_user`); partial indexes; the convention guard; the tests above; an ADR.

**Out:** sync itself, a sync cursor endpoint, conflict *resolution* policy (this makes conflicts
detectable, not resolved — per-entity rules are Rule 12 and belong to the sync design), and any
change to `original-app/`.

**Note on the existing tables:** there are no live rows anywhere, so this is a plain migration with
no backfill. That window closes at the first tenant, and the ADR should say so.
