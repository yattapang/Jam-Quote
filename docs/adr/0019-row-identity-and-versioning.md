# 0019 — Client-generated UUIDv7 ids, a version column compared on write, and tombstones

**Date:** 2026-09-24
**Status:** Accepted
**Design:** `docs/design/row-identity-and-versioning.md` (approved by the owner, 2026-09-24)
**Closes:** the first of the three Foundations gaps (brief §18 step 1)

## Context

The brief puts the *schema requirements* of offline sync in Foundations, even though sync itself is
step 4. The reason is the whole argument: **a sync model cannot be retrofitted onto rows that were
not built for it**, and there are 8 tables now versus hundreds later.

Three things were missing:

1. **The server assigned ids.** A quote priced on a phone with no signal already has lines
   referencing it. If the server assigns the id on arrival, the phone must rewrite every local
   reference afterwards — and a retried upload the server already processed creates a *second*
   quote.
2. **Nothing said which version a row was.** Two people editing the same quote, or a phone
   uploading an edit made against a stale copy, meant last-write-wins with the loser never told.
3. **A deletion left nothing behind.** To a phone that has been offline, a row deleted on the
   server is indistinguishable from one it has not been told about — so it comes back.

## Decision

**Ids are UUIDv7, generated by whoever creates the row**, from `newRowId()` in `@pryvis/core`.
Postgres keeps `gen_random_uuid()` as a default — a v4 in the data is therefore a *signal* that a
row was written by a migration or a script rather than the application, and `isRowId()` makes that
signal readable.

**A `version INTEGER` compared on every write:**
`UPDATE … SET version = version + 1 WHERE id = $1 AND version = $2`. Zero rows affected means
somebody else got there first, and the caller is told rather than having their edit vanish. One
column does optimistic concurrency and sync conflict detection.

**A `deleted_at` tombstone on tenant-owned business data**, with **partial indexes**
(`WHERE deleted_at IS NULL`) — including the per-tenant email unique index, so a deleted user's
address is not held hostage.

**The convention is a test, not a convention.** `db/test/row-convention.test.ts` discovers every
tenant-owned business table and refuses one missing either column, refuses a non-partial index on a
tombstoned table, and requires every exemption to be named with a reason and to still exist.

## Alternatives considered

**UUIDv4.** Simpler, `crypto.randomUUID()` for free. Rejected: random ids scatter inserts across
the primary-key index, and "most recent first" needs a second column. v4's one advantage — no
information in the id — matters for secrets, and a row id is not one.

**Database-assigned ids (serial or `gen_random_uuid()` as the real path).** Conventional and
simpler. Rejected: it makes an offline-created row impossible to reference until it has been
uploaded, and makes a retried upload a duplicate. Idempotent upload is the requirement; a
client-chosen id is how it is met.

**`updated_at` for concurrency.** No extra column. Rejected: clocks disagree, two writes inside
one millisecond are indistinguishable, and a backwards correction makes a stale write look fresh.
`updated_at` stays for humans and for cursors, and is not the check.

**Postgres `xmin`.** Free and automatic. Rejected: it wraps, it is not portable (Rule 10), and a
client cannot read it to send back.

**Hard deletes plus a separate tombstone table.** Keeps live tables clean. Rejected: two places to
keep in step, two queries to answer "does this row exist", and the same filtering cost moved
somewhere less obvious.

## Consequences

- **Every update is wordier**, and must carry `AND version = $n`. That is the difference between a
  lost edit and a reported conflict. **A guard that every repository does so is owed** — it cannot
  exist until a persistence layer does, and the test file says so rather than implying coverage.
- **Every query must filter `deleted_at IS NULL`.** Also owed as a guard, for the same reason.
- **A v7 id carries its creation time.** Harmless on a row; **not** harmless in a public URL. A
  share token is a separate random secret, and both the module header and this ADR say plainly that
  a row id is not a secret — because the tempting "simplification" later is to reuse one.
- **The id generator is stateful per process.** Monotonicity within a millisecond is bought with a
  counter, so two servers do not coordinate and ids from different processes inside one millisecond
  order arbitrarily between themselves. Acceptable because the ordering claim is "roughly by
  creation time" for index locality and default sort — never for deciding which write won. That is
  `version`'s job, and the test asserts the statefulness rather than leaving it implicit.
- **`@pryvis/core` now exists**, with row identity as its first inhabitant. The money, tax and
  settlement rules arrive there later as their own reviewed port (ADR 0010) — deliberately adapted,
  not copied, since the vocabulary changed.
- **The sync cursor is deliberately undecided.** `updated_at` with an id tie-break is available and
  its limit is named: it comes from a clock, so a correction or two writes in one millisecond can
  skip a row. A per-tenant monotonic sequence would fix that at the cost of a shared counter on
  every write. That belongs to the sync design; this decision only keeps both answers open.
- **No backfill was needed** because no row exists anywhere. That window closes at the first tenant,
  and a later change of this shape would need one.

## What writing it found

The convention guard's first run failed on **this migration's own work**: `app_user_tenant_id_idx`
predated it and was not partial, so a tenant's user list would have scanned rows it was about to
discard. Found because the rule is a test rather than a paragraph.

The behaviour tests' first run was refused by row-level security — they set the application role
and forgot to set a tenant. That is the isolation guard working on a careless test of mine, and the
test now operates inside a tenant the way the application does.
