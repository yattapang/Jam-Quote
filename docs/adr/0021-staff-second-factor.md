# ADR 0021 — A second factor: required of staff, offered to tenants

- **Status:** Accepted
- **Date:** 2026-09-24
- **Design:** [`docs/design/staff-mfa.md`](../design/staff-mfa.md) (approved before any code — Rule 1.1)
- **Supersedes:** nothing. Extends ADR 0013 (default-deny), ADR 0014 (password hashing),
  ADR 0016 (rate limiting), ADR 0020 (audit log).
- **Delegation (Rule 16.5), recorded after the fact and in breach:** built by **Opus in the main
  session**, with no agent and no declared decision. Rule 16.2 places "building to a precise spec"
  with Sonnet, and this had an approved design listing the very defects to plant. Under 16.5 — which
  exists because of this batch — the credential-path exception would have permitted Opus, but only if
  declared and argued beforehand. It was not. Recorded rather than tidied away, because the first
  entry under a new rule showing the rule being kept would be a small lie.

## Context

The owner's instruction: *"The passwords for employees and administrators should have MFA and any
other key minimum requirements to improve security."* Recorded as Rule 5.1.

The asymmetry is the whole argument. A tenant who loses their password loses their own data. A
staff member who loses theirs loses **everybody's**, because the console can suspend a tenant,
change pricing and impersonate a user. Tenants did not choose our staff's password hygiene, and
cannot inspect it.

## Decision

**1. TOTP (RFC 6238), written rather than installed.** Sixty lines of well-specified arithmetic
against a dependency in the credential path, read on every staff sign-in and updated by someone we
do not know. The published Appendix B vectors make "did we implement it correctly" a question with
an answer, which is the part that usually justifies a library. All six vectors are asserted, and
the fixture itself is guarded — a wrong base32 encoder would otherwise have every vector agreeing
with our own mistake.

SHA-1 is not a compromise here: it is RFC 6238's default and what every authenticator app
implements, and HMAC-SHA1's security does not rest on the collision resistance that fell.

**2. Secrets encrypted at rest with a key registry, not a single key.** A TOTP secret is a
credential equal to a password — anyone holding it generates valid codes forever — so storing it in
plaintext beside the scrypt hashes would hand an attacker with a database dump both factors. Unlike
a password it must be readable, so this is encryption (AES-256-GCM), not hashing.

More than one key on purpose. A single key **cannot be rotated**: changing it makes every row
undecryptable and forces every staff member to re-enrol, so in practice it is never changed and
"encrypted at rest" quietly means "encrypted with a key we can never change". Each row names the
key that sealed it; new secrets use the current key; a row is re-sealed at the one moment its
plaintext is in hand, on the next successful verification. The registry refuses to start with no
keys rather than falling back to plaintext, and never falls back to another key when the named one
is missing.

**The honest limit:** the key lives in configuration, never in the database, so a dump alone is
useless. An attacker holding **both** the database and the environment has the secrets. There is no
key-management service, and this is stated rather than described as "encrypted at rest" and left to
sound complete. A KMS is recorded as owed.

**3. Enrolment grants nothing until a code is produced.** An unconfirmed factor means a secret was
issued and may never have reached a phone. An abandoned enrolment may be replaced; a confirmed one
may not.

**4. Ten recovery codes, SHA-256 and unsalted, single use.** Twenty random base32 characters each
(~100 bits), generated by us, so there is no dictionary to try and no reuse across sites: a slow
hash defends against nothing here, while ten at scrypt's cost would mean 670 MB of work to enrol
one person. Claimed in a single statement so two concurrent attempts cannot both spend one, and
marked rather than deleted so "a recovery code was used" stays a fact the audit trail can point at.

**5. Replay refused by recording the step.** A code is valid for its whole 30-second step and the
drift window is ±1, so "correct" is not "unused". Without the recorded step a code read over a
shoulder or captured in transit works again. The drift window stays at ±1 (90 seconds): widening it
trades a real property for a convenience nobody asked for.

**6. Attempt limiting in two layers.** The token-bucket limiter first, before any HMAC — the
expensive work must be what is protected, and a flood must not spend the factor's own allowance.
Then five consecutive failures lock the factor for fifteen minutes. That counter lives on the
**factor, not the session**: an attacker who already has the password can open as many sessions as
they like, so a per-session counter is an allowance they reset at will. Five is chosen for a person
reading a code as it rolls over, not for an attacker; a million codes against five attempts and a
fifteen-minute lock is roughly one guess in thirty thousand per day.

**7. Enforced in the resolver, on every request.** Two refusals: `mfa-pending` (the session is
half-way through a sign-in) and `mfa-required` (the person holds a platform capability and has no
confirmed factor). The second is the one that closes the hole — a requirement living only in the
enrolment flow is a requirement that anybody who skipped the flow does not have. Both are checked
**after** suspension and deactivation, so a discarded token cannot be used to learn whether an
account has MFA set up.

Those two refusals carry a `partial` identity, which authorises nothing: the code prompt and the
enrolment page need to know whose factor to check, and refusing them outright would lock a staff
member out of the page that unlocks their account. Everything else branches on `ok` alone.

**8. Sign-in becomes two steps.** A session is issued immediately but marked `mfa_pending` in the
same statement that reads the user's state — inserting first and marking after would leave it fully
valid for the width of that gap. The half-finished state is therefore one boolean on the existing
session row rather than a signed "half token" or a server-side map, so every existing revocation
and expiry applies to it unchanged.

**9. `mfa_verified_at`, so re-authentication is answerable.** `mfa_pending` answers "ever", which
cannot answer "recently": a laptop walked away from has a session that passed a factor hours ago,
and starting an impersonation from it is exactly what a re-prompt prevents. Fifteen minutes.

**10. Audited: enrolment confirmed, recovery code used, factor locked.** A recovery code used is
the one signal that an authenticator was lost or taken. No code, and no secret, ever reaches the
audit trail — `details` is refused outright if it carries anything resembling a credential
(ADR 0020).

**11. There is deliberately no `disableMfa()`.** A lost device is recovery codes; if those are gone
too it is a re-enrolment performed by another staff member holding a specific capability, audited,
with sessions revoked. A support path that removes a factor over a phone call is the standard way
MFA is defeated in practice, and the way to not have one is to not write one. A test asserts the
method does not exist, so adding the door is a visible act.

**12. Required of staff, offered to tenants.** Requiring it of every tenant today would lock out
every existing account and make signing up harder for the contractor in the field the product is
for — a different decision, and not this one. Revisit when tenants handle other people's money.

## Consequences

- One staff member cannot lock out the team: the counter is per person, which a test holds.
- A staff member who loses their phone and their recovery codes needs another staff member. That is
  the intended cost of having no self-service removal, and it means the second staff account must
  exist before the first one is relied on.
- `MFA_TOTP_KEYS` becomes a required secret. The service register names it; without it the API
  refuses to start, which is the intended failure.
- The single message for every refusal means support cannot tell a locked account from a wrong code
  without reading the audit trail. Accepted: the alternative tells an attacker with a stolen
  password that the account exists and is protected.

## Owed, and recorded rather than implied

- The re-enrolment path (capability-gated, audited, revokes sessions), which arrives with the staff
  console.
- HTTP transport: the code prompt, the cookie, CSRF. Nothing here has a route yet.
- A key-management service in place of configuration.
- Calling `hasRecentVerification` at each dangerous action — the check exists and is tested; the
  actions it guards do not exist yet.
- WebAuthn as a stronger factor. TOTP is phishable; a passkey is not. Not today.

## Proved by planting the defect

Fourteen plants, each run against the suite and restored from a backup copy (never `git checkout`,
Rule 16), plus two comment-only controls that stayed green:

replay check removed · enrolment confirmed on issue · lock counter that never accumulates · limiter
moved after the work · secret stored in plaintext · recovery code reusable · recovery code not
scoped to its owner · distinguishable refusals · `mfa_verified_at` never stamped · rotation never
re-seals · sign-in never marks the session pending · resolver ignores a pending session · resolver
lets a capability-holder past without a factor · resolver counts an unconfirmed enrolment.
